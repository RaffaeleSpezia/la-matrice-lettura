La Matrice

The Code, the Machine and the Third Thing

We have not fully reckoned with one fundamental fact.

This time, we are dealing with a new kind of machine.

A black box for everyone.

A box that takes a combination of information as input and produces a combination as output that somehow turns out to be correct, coherent or useful.

Not because someone has written out, one by one, the rules linking that input to that output.

Not because somewhere inside there is a long hidden sequence of instructions saying:

If the user says this, answer that.

Instead, inside that box there is a representation.

A compressed, incomplete, imperfect, yet extraordinarily vast representation of our reality, our knowledge, our language, our rules, the relationships between objects, the concepts we use, and a huge part of the culture produced by human beings.

We can give it something we understand immediately.

A sentence.

An image.

A sound.

A sequence of numbers.

A program.

The description of a problem.

The machine receives that sequence, passes it through its internal structure, and produces another sequence.

And that sequence returns to our world.

Words we understand.

Code we can run.

Images we can look at.

Actions we can carry out.

In most cases, something useful.

This seems normal only because we got used to it so quickly.

But it is not normal at all.

First, the Code

For decades, we identified software with something relatively precise.

A set of instructions.

The programmer decided what should happen and described to the machine how to make it happen.

Software could be enormous, complex, full of layers of abstraction, libraries, dependencies and behaviors that were difficult to predict.

But beneath it all lay a familiar logic.

Someone had written instructions.

The code represented the machine's behavior.

The complexity could be vast, but there was still a fairly clear relationship between the program and what the program did.

If we wanted to change its behavior, we changed the code.

If we wanted to add a function, we added code.

If we wanted to understand why something happened, at least in theory we could follow the execution of the instructions.

It was difficult.

But the principle was clear.

Then, the Machine

Before software, we had the physical machine.

The engine.

The chassis.

The gears.

The turbine.

The circuit.

The computer.

The machine existed as an object.

It had a shape.

It had boundaries.

We could point a finger at it.

We could say:

This is the machine.

Software had then introduced something different.

The same physical machine could perform entirely different tasks when its program was changed.

The computer had become a universal machine.

But two levels remained easy to distinguish.

Hardware on one side.

Software on the other.

The machine.

And the code that controlled it.

That distinction has become so deeply rooted in our thinking that we still use it today.

Hardware and software.

The body and the instructions.

But perhaps it is no longer enough.

The Third Thing

A large neural model is not simply code.

Of course, code exists.

It defines the architecture.

It trains the model.

It loads the weights.

It performs the mathematical operations.

It distributes computation across the hardware.

But code alone does not contain what the machine knows how to do.

We can have two perfectly identical copies of a program running a neural network.

The same code.

The same architecture.

The same hardware.

And obtain two radically different machines by loading different weights.

One may know a language.

The other may not.

One may be able to program.

The other may recognize images.

One may be almost useless.

The other may contain an extraordinarily sophisticated representation of the world.

So where is the machine?

Not in the code.

Not entirely in the hardware.

A third thing has emerged.

A learned structure.

A numerical configuration capable of transforming inputs into outputs through an immense network of relationships.

Weights are not simply data in the traditional sense.

They are not an archive of documents.

They are not a database we can query by looking for a particular row.

Nor are they instructions.

They are the very structure through which information is transformed.

If we change that structure, we change the machine's behavior.

And yet no programmer wrote that structure directly.

It was produced.

Trained.

Brought into being.

This is the third thing.

Not just code.

Not just machine.

A learned machine.

A Machine No One Programmed Directly

That difference is enormous.

For the first time, we have built systems in which the most interesting behavior does not arise from explicit instructions written one by one.

It arises from a process.

We show the machine enormous quantities of information.

We define an objective.

We correct the error.

We modify billions of parameters.

We repeat the process an immense number of times.

In the end, we obtain something that works.

But we have not directly written what it has become.

We have built the process capable of producing it.

It is rather like the difference between making an object and creating the conditions in which something can grow.

When we write a traditional program, we build the behavior directly.

When we train a neural network, we mostly build the conditions from which behavior can emerge.

The final result can be used as a machine.

But it has not been made in the same way as the machines before it.

The Box

That is where the sense of a black box comes from.

We provide an input.

We obtain an output.

We may know the architecture perfectly.

We may know every weight.

We may observe every multiplication.

And yet that does not mean we can easily explain why a particular sequence produced exactly that answer.

There may be no single rule we can locate.

No line of code containing that sentence.

No compartment in which that answer was stored.

The answer arises as information passes through the entire configuration.

This makes the machine profoundly different from its predecessors.

Its function cannot easily be described by listing instructions.

Its function is distributed throughout its structure.

An Almost Inexhaustible Space

The possible combinations are not infinite.

We should be precise about that.

Every finite digital system has a finite number of states.

Even the largest model ever built is finite.

But the number of possible combinations is so vast that, from our practical point of view, it can become almost inexhaustible.

We can formulate a sentence no one has ever written before.

The machine can produce an answer no one prepared in advance.

We can change a word.

Change the context.

Add an image.

Change the order of the information.

Ask it to combine concepts from different fields.

Every variation can open another path.

The space of inputs is immense.

The space of internal transformations is immense.

The space of outputs is immense.

This is what creates the feeling that we are no longer dealing simply with a program.

A traditional program follows possibilities that have been designed.

This machine explores a space of possibilities it has learned.

A Representation of the World

But perhaps the most important part is not the number of combinations.

It is what the machine contains.

To produce plausible answers, it must have incorporated an enormous number of relationships.

The relationship between one word and another.

Between an object and its use.

Between cause and effect.

Between one concept and other concepts.

Between a linguistic structure and an intention.

Between a description and what that description might represent.

Of course, that representation is not the world itself.

It is not a perfect copy of reality.

It can be wrong.

It can be incomplete.

It can contain distortions.

It can produce absurd associations.

But it must still possess an internal structure rich enough to navigate different regions of human knowledge.

And it is precisely that structure that makes it interesting.

We have not simply built a system that contains information.

We have built a machine that contains relationships between pieces of information.

A Machine Without a Shape

Here another fundamental difference from the past appears.

Before, we built the physical machine.

The engine had a size.

The turbine had a size.

The computer had a size.

Once built, the object was what it was.

Of course, we could replace components.

We could improve it.

We could build a bigger one.

But its physical identity was clear.

The neural machine, by contrast, does not necessarily have a physical shape of its own.

There is no little box.

We can save the model to a disk.

We can copy it.

Move it.

Divide it.

Run it on different hardware.

Distribute its parts across multiple devices.

The same mathematical structure can exist on one server today and another tomorrow.

Hardware is the substrate that allows the machine to manifest itself.

But it is not necessarily the machine itself.

That makes the model something strange.

It is real.

It produces real effects.

It requires real energy.

It requires real memory.

It occupies real hardware.

But its form is not identical to any of those things.

The Temporary Body

When a model runs, the hardware temporarily becomes its body.

GPUs.

CPUs.

RAM.

Distributed memory.

Interconnections.

Networks.

For a few seconds, a few hours or a few years, that mathematical structure lives through that substrate.

Then it can be moved.

Duplicated.

Reduced.

Quantized.

Divided.

Modified.

The body can change without the machine's functional identity necessarily disappearing.

That is an idea worth examining closely.

Because if a machine has no fixed physical body, there is no fundamental reason it must have only one body.

Hardware Is Never Enough

And perhaps here we can understand one of the most obvious features of contemporary artificial intelligence.

There never seems to be enough hardware.

More memory.

More GPUs.

More bandwidth.

More energy.

More data centers.

More interconnections.

Every new generation seems almost immediately inadequate.

Not necessarily because we are designing hardware badly.

But because, for the first time, increasing the hardware can directly increase the size of the virtual machine.

If I build an engine, at some point the engine is finished.

I can build a more powerful one, but I am building another engine.

Here, instead, I can expand the substrate and enlarge the structure that exists on top of it.

More parameters.

More context.

More memory.

More sensory modalities.

More experts.

More pathways.

More abilities.

We can give the machine a larger body.

And immediately the machine can occupy that space.

This creates what may be a continuous hunger for resources.

But Here an Error Creeps In

From this characteristic, we have drawn an almost automatic conclusion.

If a bigger machine requires more hardware, then we must build ever larger hardware in the same place.

More GPUs in a server.

More servers in a rack.

More racks in a data center.

More data centers connected together.

It is one possible solution.

But not necessarily the only one.

It may simply be a continuation of our old way of thinking.

We are used to imagining a machine as something that must be contained.

A box.

A room.

A factory.

A building.

A data center.

But the machine we are talking about has no natural physical boundary.

We are the ones imposing that boundary on it.

Where Does the Machine End?

This question then becomes fundamental.

If a hundred devices take part in running a model, where is the machine?

In the first device?

In the hundredth?

In the network?

In the weights?

In the code?

In the traffic passing between nodes?

Or is the machine the entire system of relationships that allows information to flow through those components?

The question becomes even more interesting when we stop thinking about identical nodes.

Imagine thousands of different machines.

One has a great deal of memory.

One has a small GPU.

One has an NPU.

One holds a body of knowledge.

One specializes in vision.

Another in language.

Another in controlling a robot.

One exists on the network for only a few minutes, when energy is available.

One joins.

Another leaves.

Where, then, is the machine?

Perhaps the question itself is wrong.

Perhaps the machine no longer needs to be somewhere.

Perhaps it simply needs to exist through the network.

From Program to Organism

Here the boundary with ideas we will develop later grows thin.

If a structure can be distributed, modified, extended and allowed to grow over time, then it begins to resemble a traditional program less and less.

Not because it becomes biological.

Not because it magically acquires properties it does not possess.

But because the paradigm we need to describe it changes.

A program is written.

A machine is built.

This third thing can be trained.

It can be allowed to grow.

It can be modified without its behavior being rewritten directly.

It can be duplicated.

It can merge with other structures.

It can specialize some of its parts.

It can lose abilities.

It can acquire new ones.

It can, at least in principle, continue to transform itself.

At that point, perhaps the right metaphor is no longer only that of the machine.

The metaphor of the organism begins to appear.

Not because it is alive.

But because, to understand how it evolves, it may be more useful to speak of growth, specialization, connection and adaptation than of programming alone.

The Limits of the Box

Today's large models are still built mainly as bounded objects.

A model.

A given number of parameters.

A given architecture.

A training phase.

A version.

A release.

GPT-X.

Gemma-X.

Qwen-X.

Llama-X.

Different names for different objects.

That is understandable.

We need to freeze something in order to distribute it, measure it, compare it and sell it.

But that does not mean this must be its final form.

It could simply be the first industrially manageable form of this new machine.

Just as the earliest computers occupied entire rooms and were used as large centralized calculators.

Their original form did not represent the conceptual limit of the computer.

It was simply how we knew how to build them at the time.

Perhaps we are doing the same with models.

We discovered the third thing.

And immediately locked it inside a box.

Removing the Boundaries

This brings us to a fundamental question for La Matrice.

If the machine we are interested in is no longer merely the hardware, and no longer merely the code, why do we keep building it as though it must live inside a single box?

Why should its body be a server?

A cluster?

A data center?

Infrastructure owned by a single organization?

Why should there be a maximum size defined by the hardware that any one entity can put in one place?

Perhaps the next step is not to build an even larger box.

Perhaps it is to remove the box's boundaries.

At that point the problem changes completely.

We no longer need to ask only:

How large a model can we build?

The question becomes:

How large can a structure grow when no one is required to contain it?

And then:

Can it grow without being rebuilt from scratch?

Can it add new cells?

Can it accept new nodes?

Can it distribute parts of its knowledge?

Can it develop specializations?

Can it lose a node without losing itself?

Can it keep learning without erasing what it already knows?

Can it exist without any single individual, company or state owning the whole machine?

These are no longer merely questions about artificial intelligence.

They are questions about the architecture of the machine.

And above all, about the nature of the third thing.

We had the code.

We had the machine.

Now we have something that arises from code and uses the machine, but is not entirely identical to either.

A learned structure.

A representation capable of transforming information.

A virtual machine without a compulsory physical form.

A thing we can still choose to lock inside a box.

Or allow to grow beyond its boundaries.
